# Project Policies

Version policy, packaging, lint toolchain, and secrets — the detail behind [CLAUDE.md → Build, CI & Policies](../../CLAUDE.md#build-ci--policies).

## Node version policy

`package.json#engines` (`^22.14.0 || >=24.10.0`) is the runtime floor. The CI matrix is driven by the shared workflow's `RTLDEV_MW_CI_NODE_MATRIX` repository variable (not hardcoded here) and tracks actively-maintained Node versions.

## Package manager: pnpm only

Every script, lockfile and CI step assumes pnpm. This has already caused one real incident: `10.0.11`–`10.0.15` published with an **empty `dist/`** because the build hook was named `prepublish`, a hook pnpm never runs (only `npm install` ran it, back when the repo was on npm) — see [ci-release.md](ci-release.md), which re-confirms this directly against the live npm registry (2026-08-21). The hook is now `prepare`. Before adding any script or config, check whether it's actually an npm-era assumption that happens to work under pnpm by coincidence.

## Distribution

- `package.json#files`: `["dist", "README.md", "LICENSE"]` — only these ship. `pnpm run pack:check` (`scripts/pack-check.ts`, part of `pnpm lint`) verifies this for real on every run: packs the actual tarball and asserts it contains `dist/index.js`/`dist/index.d.ts` and none of `src/`, `tests/`, `examples/`, `.env`, or the `rtldev-middleware-php-sdk/` reference clone — not by reading `#files` and trusting it, by inspecting the tarball's own contents (`tar -tzf`).
- `package.json#exports`: `"."` only, resolving to `dist/index.js`/`dist/index.d.ts`. This enforces the single-barrel decision at module-resolution time — a deep import like `@team-internet/apiconnector/dist/CNR/Client.js` will not resolve, by construction. New surface is added as a namespaced export from the root barrel (`src/index.ts`), never as a new subpath — `"."`-only is what makes that the only route, not a reason new capability cannot be added at all.
- **`pnpm run pack:check` also installs the packed tarball into a throwaway directory outside the repo** (`os.tmpdir()`, never a repo-relative path) and imports it as `@team-internet/apiconnector` — the way an actual consumer's `npm install` would, not by relative path into `src/`. This is the gate that would have caught `10.0.11`–`10.0.15` (see "Package manager: pnpm only" above): that incident shipped a `main` pointing at a `dist/` the tarball did not contain, and nothing before this script ever built, packed, or imported the published artifact to notice. It also type-checks a minimal TS consumer (`tsc --noEmit` against the installed package, using this repo's own `tsc` binary — no second TypeScript install). Wired into `pnpm lint`, not a `.github/workflows/*` file — the shared CI workflow's `test_matrix` job already depends on `pnpm run lint`, which is the only lever this repo has into CI without editing a workflow file.
- **Because `README.md` is the only doc that ships**, every relative link in it to `MIGRATION.md`, `examples/`, or `docs/` must be an absolute `github.com/.../blob/master/...` URL instead.

## Static analysis <a id="static-analysis"></a>

`pnpm lint` = `prettier --check` + `pnpm typecheck` (`tsc --noEmit -p tsconfig.test.json`, covering `src/`, `tests/` **and** `scripts/`) + `pnpm eslint` (typescript-eslint `strictTypeChecked` + `stylisticTypeChecked`) + `pnpm fallow` (`fallow dead-code && fallow dupes`) + `pnpm run pack:check` (see "Distribution" above).

**`typescript` is pinned to `^6.0.3`, not `7.x`.** `typedoc@0.28.20` and `typescript-eslint@8.67.0` both hard-refuse to start on TypeScript 7 (`typedoc`: crashes reading `ts.SyntaxKind`; `typescript-eslint`: `"typescript-eslint does not support TS 7.0"`, tracked upstream at [typescript-eslint#10940](https://github.com/typescript-eslint/typescript-eslint/issues/10940)) — every fact in this claim, including the exact crash, was reproduced fresh (2026-08-21); see [ci-release.md → Fix 3](ci-release.md) for the verification detail rather than duplicating it here. This was investigated and initially assumed to require either waiting on upstream or a TS-6-for-eslint-only side-by-side install (the pnpm-override approach for that didn't work cleanly — the dependency in question resolves as a peerDependency, which pnpm's override mechanism doesn't reach the same way it reaches a normal dependency edge). **That assumption was wrong and cost real time before it was checked:** `noUncheckedIndexedAccess`, `verbatimModuleSyntax` and `noImplicitOverride` are TS 4.1/5.0/4.3 features respectively, not TS7-exclusive, so pinning the *project's own* `typescript` devDependency down to `6.0.3` needed zero source changes — verified with a real `tsc --noEmit`/`tsc --declaration`/`typedoc` run before committing to it, not assumed. This unblocked both tools at once with a one-line `package.json` change. Revisit if a future change genuinely needs a TS7-only feature; check that need against a real compile before reaching for a workaround again.

`eslint.config.js` deliberately overrides several `strictTypeChecked`/`stylisticTypeChecked` rules that fight this codebase's own conventions rather than catch real defects — each override carries its rationale inline:

- `no-extraneous-class` off — static-utility classes (`CommandFormatter`, `CommandRedactor`, `SensitiveFields`, `IDNCommandRewriter`, `ClientFactory`) are the deliberate PHP-parity pattern for `abstract class X { public static function ... }`.
- `dot-notation` off — bracket access on `Hash`/`StringHash` command objects (`cmd["COMMAND"]`) is the parity-preserving style for PHP's associative-array access; these are dynamic wire-format keys, not fixed properties.
- `consistent-type-definitions` off — deliberately mixed: every `*Interface.ts` file is a real `interface`, `src/types.ts`'s `Hash`/`StringHash`/`ApiCommand` are `type` aliases. Forcing one style project-wide fights the split. **Caution for future edits:** turning this rule on with `["error", "type"]` will auto-`--fix` every `*Interface.ts` file's `interface X {}` into `type X = {}` — which silently breaks any interface using `extends` (TS `type` has no `extends`; the auto-fix leaves an invalid trailing `& OtherInterface` that fails to parse). This actually happened once during this port (`ResponseInterface`/`ExtendedResponseInterface`) and was caught by the resulting parse error, not by review — if this rule is ever revisited, check every `*Interface.ts` file for `extends` first.
- `no-non-null-assertion` stays on (the `strictTypeChecked` default) — an earlier draft of this config turned it off with a blanket "every `!` follows an immediately-preceding `hasOwnProperty` guard" justification. That justification was checked by enabling the rule rather than taken on faith, and it was wrong for 2 of the 4 sites the rule actually flagged: `AbstractResponseTranslator.ts`'s two guarded sites do have an immediately-preceding `hasOwnProperty` check, but its third site's safety comes from a guard *inside the called* `resolveTemplateId()`, and `ApiDateTime.ts`'s comes from a cross-branch invariant established earlier, not an adjacent line. Each of the 4 sites now carries its own `// eslint-disable-next-line @typescript-eslint/no-non-null-assertion` with the actual, site-specific reason instead of one rule-wide comment covering all of them.
- `class-literal-property-style` off — it wants a literal-returning `get` accessor rewritten as a `readonly` field, which is exactly the shape the field-initialisation-order trap forbids (see [architecture.md#three-traps](architecture.md#three-traps)).
- Test-only relaxations (`tests/**`): `no-unsafe-member-access`/`no-unsafe-assignment` (reflection-style seam checks), `no-unused-expressions` (chai's `expect(x).to.be.true` assertion style), `require-await`/`no-empty-function` (interface-conforming async stubs/doubles that genuinely have nothing to await or do), `unbound-method` (seam specs compare method references for *identity*, never call them unbound).

`fallow` (codebase audit: unused exports/files, duplicate exports, circular imports, class-member reachability, code duplication) fills the second-analyser role Psalm plays in PHP. Config lives in `.fallowrc.jsonc`:

- **`ignoreExports`** — the CNR/IBS duplicate-export pairs that are decision 1 (siblings, not accidents) working as intended.
- **`usedClassMembers`** — methods only reachable from `tests/**` or through a chained call fallow's default analysis doesn't resolve (see [architecture.md → Known, accepted findings](architecture.md#known-accepted-findings-from-static-analysis)).
- **`ignoreFindings: ["examples/**"]`** — example files are meant to be copied, not imported, so "unreachable from any entry point" is what a correct example looks like. This key covers *dead-code* findings only; duplication needs the separate `duplicates.ignore` below.
- **`ignoreDependencies: ["@tsconfig/node22"]`** — reached through `"extends"` in `.github/linters/tsconfig.json`, which `tsconfig.json` extends in turn. fallow resolves imports, not tsconfig inheritance, so it counts zero usages; `pnpm run typecheck` fails without the package. Suppressed rather than removed, because a permanently red finding is worse than no finding — it teaches everyone to skim past output that is supposed to be empty.
- **`duplicates.ignore: ["examples/**"]`** and **`duplicates.threshold: 3.0`** — see the paragraph below.
- **`circular-dependency` has no config-level equivalent** — fallow's own guidance says inter-file rules (`duplicate-exports`, `circular-dependencies`, `re-export-cycle`) can only be overridden per-file via a `// fallow-ignore-file` comment, never through config. The two `Response.ts` files carry that comment for exactly one accepted, structural cycle (see architecture.md).

`fallow dupes` is gated on **`duplicates.threshold: 3.0`** (a percentage of duplicated lines), and `fallow dead-code` fails on any unsuppressed finding *except* the "unused dev/optional dependency" kind, which prints a `✗` and still exits `0` — verified directly (2026-08-21), and the reason `@tsconfig/node22` had to be suppressed by config rather than left to the gate.

3.0% is the measured floor, and it is entirely the three CNR/IBS sibling clone groups (`Response`, `ResponseTemplateManager`, `SocketConfig`) that decision 1 keeps on purpose. **Re-measure and move the number if a real refactor changes the floor; never raise it to silence a finding.**

A percentage, deliberately, rather than `duplicates.ignoredClones`. That was tried first and is unsafe here: clone keys sharing a fingerprint are distinguished by a positional `-N` suffix assigned over the *reported* set, so suppressing one group renumbers the rest and a stale key silently absorbs the next new clone. Verified by planting a duplicate pair in `src/` — with the four `ignoredClones` keys that made the run clean, the planted clone was swallowed and the gate still exited `0`. The threshold catches it (3.0% → 3.3%, exit `1`), because new duplication cannot help raising the number. Both directions were re-checked after the switch: planted clone exits `1`, removing it exits `0`.

The pre-config baseline capture (evidence the old flat CNR-only modules were fully absorbed with nothing orphaned) was a scratch working doc for this review, not a durable repo file — its content belongs in this change's PR description, not a root-level `.md` left for the next reader to wonder whether it's still current.

## Secrets <a id="secrets"></a>

Scheme: `RTLDEV_MW_CI_USER_{CNR,IBS,MONIKER}` / `RTLDEV_MW_CI_USERPASSWORD_{CNR,IBS,MONIKER}`, plus the CNR role pair (`RTLDEV_MW_CI_ROLE_CNR`/`RTLDEV_MW_CI_ROLEPASSWORD_CNR`) — matching PHP's scheme and the org's CI secrets. `.env.example` is the template; copy it to `.env` (gitignored) to run `pnpm test:record` or the `pnpm demo:*` scripts against real OT&E credentials.

**The default `pnpm test` needs no credentials at all.** Committed cassettes plus `nock.disableNetConnect()` make it offline by construction — see [testing.md](testing.md). Credentials are needed only by `pnpm test:record`, the `pnpm demo:*` scripts, and the one `node:http` loopback spec.

The shared CI workflow currently maps `secrets.RTLDEV_MW_CI_USER_CNR` → `env.CNR_TEST_USER` for this repo specifically — a rename this repo's tests no longer need, since nothing reads `CNR_TEST_*` any more. Cleaning that up, and adding the IBS/Moniker secret pass-through the shared workflow doesn't yet have, is a companion change in `rtldev-middleware-shareable-workflows` (a separate repository) — raise it alongside, not instead of, any change here that starts depending on it.

**Verified by reading `node-sdk-test.yml` in that repo's actual checkout (2026-08-21):** the `test_matrix` job's `Tests` step sets exactly `CNR_TEST_USER: ${{ secrets.RTLDEV_MW_CI_USER_CNR }}` and `CNR_TEST_PASSWORD: ${{ secrets.RTLDEV_MW_CI_USERPASSWORD_CNR }}` — no IBS/Moniker equivalent present, confirming both halves of this claim. The same file also confirms `test_matrix`'s `needs: lint` (the "one lever into CI" claim in "Distribution" above) and the `RTLDEV_MW_CI_NODE_MATRIX` variable driving the matrix (the Node version policy claim above).

**Rotate the OT&E credentials that were sitting in this devcontainer's working-tree `.env`.** It was never committed (gitignored throughout, absent from history), but it sat readable on disk with real values for long enough during this port's development that treating those specific credentials as still-confidential is the wrong assumption — rotate them with each brand before relying on this environment again. This is an action for whoever holds the OT&E accounts, not something fixable from a diff; do not read or print `.env`'s contents as part of doing it.

### `.devcontainer/devcontainer.json` host mounts — accepted, not fixed

`mounts` binds three host paths into the container beyond the pre-existing `~/.gitconfig`:

- `${localEnv:HOME}/.ssh` (readonly) — lets the container's `git` use the host's own SSH keys for clone/push against private repos, since the container has none of its own.
- `${localEnv:HOME}/.claude` — shares this Claude Code CLI's local config/session state between host and container, so an agent session started on the host and one started inside the container see the same auth and history.
- `${localEnv:HOME}${localEnv:USERPROFILE}` → `/WSL_USER` — a WSL-specific idiom: `HOME` is empty on native WSL2 and `USERPROFILE` is empty outside Windows/WSL, so exactly one of the two is non-empty per platform and the concatenation resolves to whichever one applies, mounting the Windows-side user profile (reachable from WSL) into the container. On a non-WSL host this duplicates the plain `$HOME` mount instead.

Both risks a reviewer would flag are real, not overlooked: a contributor without `~/.ssh` or `~/.claude` on the host gets a container that fails to start rather than a graceful skip (Docker bind mounts require the source to exist), and any of these three paths — private SSH keys included — is reachable by anything that runs inside the container, including a compromised extension or a malicious `postCreateCommand`/dependency script. Accepted anyway for this repo's actual contributor base (Team Internet engineers, on the org's own machines, already running Claude Code and authenticating over SSH day to day) rather than reworked into something more portable — revisit if the contributor base broadens beyond that assumption, or if a specific incident traces back to one of these mounts.
